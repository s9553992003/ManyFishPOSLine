# LINE LIFF 外帶點餐實作路線

> 2026-10-02 實作狀態：本機 Python LINE API、獨立 LIFF 顧客／預約後台及 connected POS 收件匣已完成並驗證；歷史未勾選步驟保留為原計畫，實際檔案／契約以 LINE_API 與本機驗證紀錄為準。真實 LINE／全支付、PostgreSQL 正式訂單與公網部署尚未完成。

> 2026-10-01 目錄決定：LIFF 顧客網頁與測試位於並列的 ManyFishLINE/web/liff/；共用雲端實作仍位於 ManyFishPOSAndroid/cloud/，Android 收件匣仍位於 ManyFishPOSAndroid/app/。文中的相對程式路徑以各自所屬專案為根目錄。此副本是 LINE 專案規劃入口；Android 原文件保留供整合參考。

## 跨階段驗收線

1. 顧客送單後只產生一個 `LINE_LIFF` 正式 `orderId`；線上未付款單在 POS 可見但不進製作佇列，到店付款單立即進佇列且標未付款。
2. 前端改金額、用同鍵改品項、重複付款通知、兩台 POS 同時改狀態，均不能產生重複訂單、第二筆有效收款或錯誤的已付款狀態；平台實際重複扣款須完整保留證據並列入異常對帳。
3. POS 離線後，雲端保留訂單；重連用游標補齊。既有 demo APK 仍無 `INTERNET` 權限，舊 Room 資料與現金單不受影響。
4. 全支付未經平台可信查詢確認時維持 `PAYMENT_UNCERTAIN`，不能把導向回頁當成功，也不能改成現場收款。

## 2026-09-26 文件審查修正與驗收對照

以下已同步至規格及各實作計畫；代表文件修訂完成，不代表程式或測試已完成。

| 修正 | 實作驗收位置 | 必要案例 |
| --- | --- | --- |
| 付款不可倒退 | 核心 Task 3；網頁 Task 4 | 已付後延遲 FAILED/UNKNOWN、舊嘗試事件、製作中重複成功不重設狀態。 |
| 每單唯一有效收款 | 核心 Task 2–3 | 兩個不同成功交易僅一筆有效收款；第二筆扣款證據與 paymentException 仍保留；同時僅一個未終止嘗試。 |
| 安全取消 | 核心 Task 3、5；網頁/POS 狀態 | 查詢未付後付款成功、取消後遲到成功、無終止證據維持 CANCEL_PENDING；不自動重新製作。 |
| 已收款才可完成 | 核心 Task 3；POS Task 3–4 | 到店未付可製作但不可取餐完成；收款與完成競爭仍保持一致。 |
| 送單回覆遺失復原 | 核心 Task 3、5；網頁 Task 2、4 | 已提交→回覆遺失→重載→菜單變更／暫停→用原鍵恢復；404 只可原鍵原請求重試。 |
| POS 跨店隔離 | POS Task 1–4 | A→B／重配對／環境切換，同 ID、同游標及遲到回應均不污染新範圍。 |

## 尚需外部材料

- 全支付商家線上付款介接文件、測試環境、商戶資格和密鑰。
- LINE Login／LIFF 測試 channel、`openid` scope、公開 HTTPS endpoint。
- GCP project／billing account、預算、網域與維運人員。部署商已於 2026-09-27 選定 GCP；Cloud Run、Cloud SQL PostgreSQL、備份與 Secret Manager 的建議配置見 [GCP 部署規劃](../../../../ManyFishPOSAndroid/docs/GCP_DEPLOYMENT_PLAN.md)，尚未建立實際環境。

上述外部材料只阻擋對外端對端驗證與正式付款；本地契約、網頁及 POS 開發可用虛構資料繼續。

> 架構相容要求：實作前遵循規格的「現有架構相容約束」；沿用已存在的 connected／IDoo、Android 分層、Room 舊資料與 Python 雲端，新增通路不得覆蓋既有功能。
